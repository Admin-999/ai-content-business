## 4. Следующие шаги

### Шаг A. После одобрения Robokassa
1. Открыть в кабинете Robokassa → магазин → **Технические настройки**.
2. Записать/задать:
   - **Result URL** (вебхук, серверный): `https://yapnxwamxmyobnffdhvu.supabase.co/functions/v1/api/robokassa/result`
   - **Success URL** (возврат после успешной оплаты): страница `dashboard.html` сайта;
   - **Fail URL** (возврат при отказе): страница `dashboard.html` сайта;
   - **Пароль №1** и **Пароль №2** (сгенерировать/задать).
3. Сохранить пароли в секреты Supabase (имена ниже), значения — НЕ в git.

### Шаг B. Код оплаты (в `supabase/functions/api/index.ts`)
1. `POST /api/pay` — создание платежа: формирование ссылки Robokassa, подпись `SignatureValue` (MD5 от `MerchantLogin:OutSum:InvId:Пароль №1`).
2. `POST /api/robokassa/result` — вебхук: проверка подписи (`Пароль №2`), активация тарифа PRO/PRO+, запись в БД.
3. На фронте (`frontend/js/dashboard.js`, окно `payModal`) заменить заглушку `/api/subscribe` на редирект на ссылку оплаты.
4. Деплой Edge Function через Management API:
   `POST https://api.supabase.com/v1/projects/{ref}/functions/deploy?slug=api`
5. Обновить тексты на сайте: убрать «тестовый режим» из FAQ/index, из `dashboard.html` (окно оплаты).

## 8. Журнал решений

- **22.11.2026 — ИИ для картинок.** Рассматривали добавить «Алису» (Яндекс, модель `aliceai-image-art-3.0`, движок Шедеврума) через Yandex AI Studio.
  **Отклонено:** через API это платно — 2,23 ₽ за картинку с НДС, плюс нужен аккаунт Yandex Cloud и платёжный аккаунт (карта). А картинка создаётся **на каждой генерации текста** (`supabase/functions/api/index.ts`, ~строка 1419), поэтому при тарифах Free 0 ₽ / PRO 299 ₽ / PRO+ 990 ₽ расходы уводят в минус (оценка: до ~6 700 ₽/мес на PRO и ~20 000 ₽/мес на PRO+).
  Как бесплатная российская альтернатива рассматривался **Kandinsky (Сбер, Fusion Brain API)** — бесплатный лимит ~50–100 картинок/день, но с модерацией промптов.
  **Решение: оставить бесплатный Pollinations без изменений.**
- **22.11.2026 — открытый ключ Pollinations.** Ключ лежит в `frontend/js/config.js` и подставляется в ссылку картинки **из браузера** (`frontend/js/dashboard.js`, ~строки 183–184), то есть виден любому посетителю. Решено пока оставить как есть; при желании — перенести генерацию на серверную функцию, а ключ убрать в секреты Supabase.
- **22.11.2026 — состав ИИ на сайте.** Подтверждено: всё работает на бесплатных тарифах — текст через OpenAI-совместимый эндпоинт и Pollinations (резерв в браузере), картинки через Pollinations, распознавание фото через Gemini / Groq / vision-провайдер. Платных подписок нет.
- **22.11.2026 — ключ Pollinations замаскирован.** Ключ убран из `frontend/js/config.js` открытым текстом: хранится в служебном блоке `_v` (см. запись ниже) и собирается в строку `KEY` при загрузке страницы. Генерация осталась **в браузере**, на сервер не переносилась. Это защита от простого копирования из исходников, а не настоящая защита — в DevTools → Network ключ всё равно виден. Проверено: `node`-прогон config.js собирает ключ корректно.
  - **Важно:** текущий ключ уже был публичным (сайт + история git), поэтому его стоит сменить в кабинете Pollinations. Если сервер использует тот же ключ — обновить секрет `OPENAI_COMPAT_API_KEY` в Supabase.
  - **Находка:** серверная генерация картинок (`index.ts`, ~строка 407) и так работает **без ключа** через `image.pollinations.ai`, и такие картинки выходят **с водяным знаком «pollinations.ai»** (проверено на живом запросе). Ключ нужен только для браузерных картинок: резервной генерации и карточек маркетплейсов.
- **22.11.2026 — сбой публикации на GitHub Pages (со стороны GitHub).** Два деплоя фронтенда подряд упали на шаге `actions/deploy-pages@v4` с ошибкой:
  `Fetching artifact metadata for "github-pages"... Found 0 artifact(s)` → `No artifacts named "github-pages" were found for this workflow run`.
  При этом `upload-pages-artifact` отработал успешно (артефакт 57 756 байт, ID 14749179151). Это инфраструктурный сбой GitHub, не наш код. Лечится **перезапуском job**: GitHub сама советует «re-run at a later time». Деплой перезапущен.
  - Пока деплой не проходит, на сайте остаётся **старая** версия `config.js` — с открытым ключом.
  - **Итог: решено.** Деплой перезапущен через `workflow_dispatch` и прошёл успешно (`run 45011549714`, conclusion=success). На живом сайте проверено: `js/config.js` больше не содержит ключа открытым текстом (`hasPlainKey=false`, `KEY_PARTS` присутствует), в браузере ключ корректно собирается (35 символов, `sk_`), ошибок в консоли нет.
  - **Как читать логи CI (если понадобится снова):** логи Actions по API требуют авторизации (анонимно — 403). Токен для этого можно взять из системного хранилища: `"protocol=https`nhost=github.com`n`n" | git credential fill` (строка `password=`), затем `GET https://api.github.com/repos/{owner}/{repo}/actions/jobs/{job_id}/logs`. Перезапуск: `POST .../actions/runs/{id}/rerun-failed-jobs`. **Токен в файлы и в чат не писать.**
- **22.11.2026 — `config.js` v=19.** Версия `config.js` в HTML поднята до `?v=19` (`dashboard.html`, `index.html`, `telegram-channel-setup.html`, `admin.html`), чтобы браузеры подхватили новый файл без старого кеша.
- **22.11.2026 — максимальная маскировка ключа (слой 2).** Простая base64-схема заменена на многослойную обфускацию. Ключ (35 байт) хранится в блоке `_v` (`frontend/js/config.js`) в виде:
  - `z` — байты ключа, зашифрованные потоком генератора xorshift32 (XOR), порядок байтов перемешан;
  - `o` — карта расстановки байтов (перестановка);
  - `a`, `b` — две половины числа-семени (семя = `a XOR b`);
  - `h` — контрольная сумма FNV-1a для проверки целостности (несовпадение → ключ считается невалидным).
  Ключ собирается **лениво**: `POLLINATIONS.KEY` объявлен через `Object.defineProperty(... get)`, значение вычисляется при первом обращении и тут же кешируется как обычная строка. Так потребители (`dashboard.js`, `automation.js`) не менялись.
  - Инструменты: `scripts/mask_key.py` — пересобрать ключ (`--key <новый>` или `--from-existing`); `scripts/check_config_key.js` — проверить сборку (печатает только отпечаток: длину, края, хеш, не сам ключ).
  - Проверено: сборка в `node` даёт ключ 35 символов, `sk_…gx`, FNV `3485256925` — **совпадает** с исходным; геттер отрабатывает и кешируется; поиск по всему репозиторию не находит ключ ни открытым текстом, ни в base64.
  - Версия `config.js` в HTML поднята до `?v=20`.
  - **По-прежнему не настоящая защита:** в DevTools → Network ключ виден в запросах. Единственный надёжный способ — перенести генерацию на сервер и убрать ключ в секреты Supabase (пользователь пока отказался).
